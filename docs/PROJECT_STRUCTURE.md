# Linier CRM Management System 项目结构标准

## 1. 结构目标

项目结构必须服务于福建利尼尔工业装备有限公司内部 CRM 的合同功能。系统采用单组织业务模型和清晰的模块边界；未经书面批准，不引入多租户 `workspace`/`tenant` 分层，也不建立通用 SaaS 扩展体系。

## 2. 目标目录

```text
.
├── apps/
│   ├── api/                         # 后端应用与 HTTP 入口
│   └── web/                         # 内部管理端 Web 应用
├── packages/
│   ├── config/                      # 共享工程配置
│   ├── contracts/                   # API Schema 与共享类型
│   └── ui/                          # 复用界面组件
├── modules/
│   ├── identity/                    # 认证、用户、角色、部门
│   ├── audit/                       # 操作日志
│   ├── master-data/                 # 产品、供应商、原料、价目表
│   ├── customer/                    # 客户、联系人、公海、查重
│   ├── sales/                       # 商机、跟进、拜访、签到、报价
│   ├── order/                       # 订单申请、阶段、销售出库
│   ├── expense/                     # 报销申请
│   └── insight/                     # 经营数据、绩效数据
├── database/
│   ├── migrations/                  # 有序且不可变的数据库迁移
│   └── seeds/                       # 开发与测试的确定性种子数据
├── docs/                            # 项目治理与工程标准
├── scripts/                         # 可重复执行的仓库脚本
└── tests/                           # 跨模块集成与端到端测试
```

框架选型可调整目录细节，但不得改变合同模块边界。若应用框架要求模块位于 `apps/api/src/modules/` 等目录，应保持相同模块名称和依赖规则。

## 3. 模块职责

| 模块          | 合同职责                         | 不得承担的职责                          |
| ------------- | -------------------------------- | --------------------------------------- |
| `identity`    | 认证、用户、角色、部门和数据权限 | SaaS 租户、workspace 计费或租户生命周期 |
| `audit`       | 关键操作留痕与授权查询           | 业务数据编辑或日志篡改入口              |
| `master-data` | 产品、供应商、原料、价目表       | 客户、报价或订单流程                    |
| `customer`    | 客户、联系人、公海、查重         | 营销自动化或客服工单                    |
| `sales`       | 商机、跟进、拜访、签到、报价     | 订单出库或机器学习预测                  |
| `order`       | 订单申请、阶段和销售出库         | 合同外采购、库存或物流系统              |
| `expense`     | 报销申请                         | 通用财务总账或薪资系统                  |
| `insight`     | 经营数据和绩效数据               | 合同外预测模型或数据产品                |

## 4. 依赖规则

- 应用可以依赖共享包和业务模块；共享包不得依赖应用或具体业务模块。
- 业务模块通过应用服务或明确契约协作，不得直接修改其他模块的数据表。
- `identity` 提供用户、角色、部门和权限判定；业务模块不得自行复制权限体系。
- `audit` 接收关键操作事件；业务模块不得提供修改或删除审计记录的普通入口。
- `insight` 只读取合同模块产生的已授权业务事实，不得成为新的主数据来源。
- 领域逻辑必须与 HTTP Handler 和 UI 组件分离；数据库访问必须通过仓储或应用服务封装。
- 禁止循环依赖。跨模块事务必须明确一致性边界、失败补偿和测试。

## 5. 数据与权限边界

- 核心组织结构是部门及其上下级关系，不是租户或 workspace。
- 业务记录应包含负责人、所属部门及必要的创建/更新时间字段，以支持本人、部门和公司级数据权限。
- 权限校验必须在服务端完成，并覆盖查询、导出、新增、修改、审核和状态流转。
- 金额使用最小货币单位或数据库定点数，并明确币种与舍入规则；不得使用浮点数表示金额。
- 操作日志必须记录关键业务对象标识、操作者、动作、时间和结果，同时排除密码、令牌等敏感内容。

## 6. 命名与测试

- 目录及非组件源文件使用 `kebab-case`，除非框架工具另有强制要求。
- 类型和 UI 组件使用 `PascalCase`，变量和函数使用 `camelCase`，常量使用 `UPPER_SNAKE_CASE`。
- 名称必须表达合同业务语义，不使用 `tenant`、`workspace` 等未经批准的抽象。
- 单元测试优先与实现同目录；跨模块流程和端到端测试放入 `tests/`。
- 每个模块必须包含角色权限、部门数据范围和操作日志的测试。
