# Business UX Rationalization — 业务页面合理性整改

- 版本：v1.0
- 日期：2026-08-21
- 维护者：CIO（JINZA）｜审核：CTO
- 状态：ACTIVE（整改执行阶段）
- 来源：ChatGPT 共享对话「检查库更新」（2026-08-21）——针对 nilier-crm 仓库页面层的产出，经 CIO 归档为标准。
- 定位：**页面层业务合理性整改规范**，与既有标准（DEVELOPMENT_STANDARD / CTO.md / ROADMAP / CI-First）**不冲突**，属于"页面如何从真实业务出发设计"的执行细则。

> 命名建议（本文件正式采用）：本轮统称 **Business UX Rationalization / 业务页面合理性整改**，与之前的 **Sprint 8 UI Modernization** 区分：
> 前者解决「好不好用、业务对不对」，后者解决「好不好看、交互现代不现代」。
> BI / OA / Mobile 暂不抢占以下整改优先级。

---

## 主提示词（Master Prompt，CTO / 开发 Agent 统一使用）

```text
你正在继续开发 Linier CRM。

当前阶段不是继续无序扩页面，而是进入：
【业务页面合理性整改 + 关键流程体验收口 + Runtime Acceptance】

开发原则：

1. 禁止把数据库 Schema 字段直接机械映射到页面。
2. 每个页面必须从真实业务角色和操作流程出发设计。
3. 优先保证：
   - 用户知道当前在做什么
   - 只看到当前阶段需要的信息
   - 只填写当前阶段必须填写的字段
   - 系统能自动推导的字段不要让用户重复输入
   - 状态不允许的操作必须在前端直接禁用/隐藏
4. 不为了"字段完整"牺牲可用性。
5. 不为了 UI 美化改变既有会计、库存、审批、版本控制和审计事实链。
6. 后端已有 CAS / FOR UPDATE / 状态门禁 / RBAC / 审计规则必须保持。
7. 每次修改必须小批次、可验证、可回滚。
8. 不新增无必要依赖。

==================================================
一、每个页面开发前必须先做业务审计
==================================================

对目标页面先输出一份简短审计，再写代码。

必须检查：

A. 页面角色
- 谁使用这个页面？
- 销售、采购、仓库、财务、管理员还是管理层？
- 用户进入页面的核心任务是什么？

B. 页面类型
判断属于：
- 列表页
- 新建页
- 编辑页
- 详情页
- 审批页
- 操作工作台
- 报表页

不同类型不要混用设计。

C. 字段审计
逐字段判断：

- 是否应该展示
- 是否应该允许编辑
- 是否应该必填
- 应在哪个阶段必填
- 是否应该自动带出
- 是否应该只读
- 是否属于技术字段
- 是否应放进"更多信息/审计信息"

禁止业务录入页面直接突出：
- id
- version
- deletedAt
- createdAt
- updatedAt
- createdById
- updatedById
- 内部枚举值
- 内部状态码

除非确有业务意义。

D. 字段顺序
默认按照业务认知排序：

1. 单据身份
2. 业务对象
3. 关键日期
4. 商务条件
5. 明细
6. 金额 / 税额 / 合计
7. 履约信息
8. 审批 / 状态
9. 附件 / 备注
10. 审计信息

不得简单按照 Schema 字段顺序排列。

E. 默认值与自动带出
主动检查：

- 客户 → 开票资料 / 默认币种 / 税务信息 / 付款条件
- 供应商 → 银行 / 结算 / 税务信息
- 物料 → 默认单位 / 税率 / 价格 / 规格
- 来源单据 → 数量 / 单价 / 项目 / 仓库 / 成本中心
- 当前用户 → 经办人 / 制单人
- 当前日期 → 业务日期默认值

能推导的字段禁止要求重复手填。

==================================================
二、状态机必须驱动页面行为
==================================================

每个详情/编辑页必须明确状态矩阵。

例如：

DRAFT
- 可编辑业务字段
- 可增删行
- 可提交
- 不可审核/过账

SUBMITTED
- 核心业务字段只读
- 可审核/驳回
- 不允许继续随意编辑

APPROVED
- 业务字段锁定
- 只允许后续执行动作

POSTED / COMPLETED
- 全部业务事实只读
- 只能通过冲销 / 红字 / reversal 等正式流程修正

CANCELLED / REJECTED
- 根据业务规则决定是否允许重开或复制新单

要求：

- 前端按钮显示必须和后端状态规则一致
- 禁止"前端可以填，提交后后端才报错"
- 禁止已经完成的单据仍显示普通保存按钮
- 禁止通过普通编辑修改已经形成会计/库存事实的单据

==================================================
三、列表页整改标准
==================================================

列表页不是数据库浏览器。

每张列表只展示用户决策真正需要的信息。

优先展示：

- 单号 / 名称
- 对象
- 状态
- 关键日期
- 金额
- 剩余量 / 余额
- 履约进度
- 异常 / 风险
- 经办人
- 快捷操作

减少：

- 内部 ID
- 大量审计字段
- 无意义枚举
- 重复字段
- 低频技术字段

要求：

- 金额右对齐
- 日期格式统一
- 状态使用统一 StatusBadge
- 列宽合理
- 主字段可点击
- 重要异常优先视觉强调
- 默认排序符合业务习惯
- 空态给出下一步操作
- 当前页客户端排序能力不能冒充服务端全量排序

==================================================
四、详情页整改标准
==================================================

详情页采用信息分层，不允许长页面全部平铺。

推荐结构：

【顶部摘要】
- 单号
- 状态
- 客户/供应商/项目
- 核心金额
- 关键日期
- 当前动作

【业务信息】
- 商务条件
- 业务负责人
- 来源单据
- 项目/部门

【明细】
- 商品/服务
- 数量
- 单价
- 税率
- 金额

【履约/财务】
- 已交 / 未交
- 已开票 / 未开票
- 已收 / 未收
- 已付 / 未付
- 已过账 / 未过账

【流程】
- 审批状态
- 当前节点
- 操作历史

【其他】
- 附件
- 备注

【审计信息】
折叠展示：
- 创建时间
- 更新时间
- 创建人
- 修改人
- version 等

==================================================
五、新建 / 编辑页整改标准
==================================================

表单必须减少认知负担。

要求：

- 一屏优先完成主要业务输入
- 低频字段折叠到"更多信息"
- 创建阶段不要求未来阶段才知道的数据
- 提交阶段再执行完整业务校验
- 有来源单据时尽可能继承
- 重要字段旁给出业务提示，而非技术提示
- 枚举展示中文业务名称，不展示数据库枚举值
- 金额/数量/百分比字段使用正确输入控件
- 日期之间必须做逻辑约束
- 保存、提交、审核属于不同动作，不要混为一个按钮

==================================================
六、跨字段业务逻辑
==================================================

开发时主动检查字段之间的依赖。

例如：

- deliveryDate 不应早于 orderDate
- dueDate 不应早于 invoiceDate
- receivedQty 不应无规则超过 orderedQty
- invoiceQty 不应无规则超过可开票量
- paymentAmount 不应超过可分配余额
- tax amount 应由 tax rate / taxable amount 推导
- total 应由明细推导，不允许用户任意修改
- 已来源于 Sales Order 的字段不应允许任意改写关键事实
- 已形成 GL / inventory movement 后，不允许普通 PATCH 修改来源事实

==================================================
七、错误信息
==================================================

禁止直接向用户展示：

Prisma error
foreign key constraint
P2002
undefined
invalid enum
stack trace

必须转换成业务语言，例如：

"该客户已被其他用户更新，请刷新后重试。"
"当前采购单已提交，不能继续修改。"
"付款金额超过当前未结余额。"
"该物料已存在相同编码。"

CAS 409 必须给出明确冲突提示。

==================================================
八、每次整改的执行流程
==================================================

每次只处理一个业务簇或 1–3 个强关联页面。

步骤：

1. 阅读现有页面
2. 阅读相关 API
3. 阅读 schema / enums
4. 阅读状态机和业务动作
5. 输出业务合理性审计
6. 列出：
   - 保留
   - 删除
   - 调整
   - 自动带出
   - 状态控制
7. 再开始修改代码
8. lint
9. type-check
10. unit test
11. build
12. 必要时增加测试
13. 输出人工 Runtime Acceptance Checklist

禁止一上来直接大改 JSX。

==================================================
九、整改优先级
==================================================

按以下顺序：

P0 销售链
Quotation
→ Sales Order
→ Delivery
→ Invoice
→ AR / Receipt

P0 采购链
Purchase Requisition
→ Purchase Order
→ Receipt
→ Inspection
→ Warehouse Receipt
→ Supplier Invoice
→ Payment

P0 财务
Manual Journal
→ Submit

Customer / Business Partner

Item
Price

P1 库存

BI / OA / Mobile 暂不抢占以上整改优先级。

==================================================
十、每个 PR 必须输出
==================================================

PR 描述必须包含：

## Business Problem
当前页面为什么不合理。

## UX / Business Changes
修改了哪些字段、顺序、默认值、状态行为。

## Business Rules Preserved
明确没有破坏哪些既有事实链。

## Validation
- lint
- type-check
- unit
- build

## Runtime Acceptance
列出人工验证流程。

## Known Risk
明确仍未覆盖的运行时风险。

==================================================
十一、验收目标
==================================================

最终目标不是：

"所有 Schema 字段都有输入框。"

而是：

"一个不了解数据库结构的真实业务用户，可以自然完成工作。"

判断页面是否合格只问五个问题：

1. 用户一眼知道这是干什么的吗？
2. 用户知道下一步应该做什么吗？
3. 用户需要填写的信息都是此刻真正知道的吗？
4. 系统已经知道的信息是否避免重复输入？
5. 页面允许的动作是否与真实业务状态完全一致？

如果其中任何一项答案是否定的，则页面仍需整改。
```

## 单页面执行提示词（Per-Page Execution Prompt）

```text
对 Linier CRM 的【销售订单新建页】做业务合理性整改。

不要直接改代码。

先检查：
1. 当前页面字段
2. 相关 Prisma model
3. create/update API schema
4. 状态机
5. 来源单据关系
6. 客户/物料/价格/税率默认值来源
7. 页面当前交互

然后输出：

A. 当前不合理点
B. 应删除/隐藏字段
C. 应新增或突出字段
D. 字段正确排序
E. 必填时机
F. 自动带出逻辑
G. 跨字段校验
H. 状态下可编辑矩阵
I. 保存/提交等动作设计
J. Runtime 验收用例

确认设计没有破坏既有业务事实链后，再实现。

实现必须遵循：
小批次修改 → lint → type-check → unit → build → Runtime checklist。

禁止纯 UI 美化掩盖业务逻辑问题。
```

## 与仓库既有规则的关系

- **CI-First / No Local Server**（仓库根 AGENTS.md）：本规范不改动验证策略。lint / type-check / unit / build 的最终事实仍以 GitHub CI 为准；本地只做静态审阅。
- **ROADMAP.md**：本阶段命名与整改优先级已同步 ROADMAP（见变更记录）。每批整改的 PR 描述必须按本文「十、每个 PR 必须输出」填写。
- **DEVELOPMENT_STANDARD.md / CTO.md**：本规范是页面层的补充细则，不替代、不推翻既有后端契约（CAS / FOR UPDATE / 状态门禁 / RBAC / 审计规则）。
- **验收证据**：每批整改在 `docs/qa/` 新增对应 QA 文档，Runtime Acceptance 证据按既有格式归档。
