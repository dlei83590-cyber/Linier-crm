# ADR-0004: Workflow Foundation Architecture

- 状态：已接受
- 日期：2026-08-05
- 决策者：CIO（依据企业审批业务设计）+ CTO 审核
- 分支：feature/sprint3-platform-foundation（PR #待创建）

## 背景

Sprint 4–7 将落地销售 / 采购 / 库存 / 财务等业务模块，均需要审批流
（报价审批、合同审批、采购审批、付款审批、费用报销）。若各业务模块各自实现审批，
必然导致重复代码与不一致的状态机，后续重构成本极高。

因此 Sprint 3A 先行建设 **Workflow Foundation（工作流底座）**，为 Sprint 4–7 提供
统一审批能力，业务模块只负责"定义流程 + 发起实例"，不再关心流转细节。

## 决策

### 1. Workflow Definition 与 Workflow Instance 分离

| 概念 | 模型 | 职责 |
| --- | --- | --- |
| 流程模板（一次定义，多次使用） | WorkflowDefinition + WorkflowStep + WorkflowCondition | 定义步骤、审批人类型、审批模式、条件 |
| 业务实例（每次审批一条） | WorkflowInstance + WorkflowAction + WorkflowHistory + Approver | 某张单据的一次实际流转 |

- 定义是静态的（版本化、可发布/归档）；实例是动态的（状态机流转）。
- `WorkflowInstance.businessType + businessId` 唯一（同一单据只允许一个进行中的实例）。
- 定义发布后禁止修改关键结构（code/module/steps），只能通过新版本演进，避免影响运行中实例。
- 备选方案：合并为单表（Definition 内嵌 Instance 状态）。放弃原因：模板与实例生命周期、权限、查询模式差异大，单表会造成状态污染与并发锁放大。

### 2. Approval Engine 与 Workflow Engine 解耦

- Workflow Engine（本轮）：定义流程 + 实例状态机（SUBMIT/APPROVE/REJECT/RETURN/TRANSFER/DELEGATE/WITHDRAW/TERMINATE/COMMENT）。
- Approval Engine（第二批）：Approver / ApproverGroup / Delegate / Escalation / Timeout / Reminder，负责"谁来批、超时怎么办、怎么升级"。
- 两个领域解耦：Workflow 只关心流转，Approval 只关心审批人策略；Approval 通过 `instanceId + stepNo` 挂接到 Workflow 实例。
- 备选方案：合并为一个引擎。放弃原因：审批人解析（角色/部门/组）与流程流转（步骤推进）变化频率与关注点不同，合并会导致单模块过重、测试困难。

### 3. 动作统一建模

- 所有业务模块共用一套动作枚举 `WorkflowActionType`：
  SUBMIT / APPROVE / REJECT / RETURN / TRANSFER / DELEGATE / WITHDRAW / TERMINATE / COMMENT。
- 业务模块禁止自定义动作；新动作必须走统一枚举扩展（集中管理，CTO 规则）。
- 每个动作写入 `WorkflowAction`（动作记录）+ `WorkflowHistory`（前后状态、IP、设备、浏览器、耗时、备注、附件）。
- 备选方案：各业务模块自定义动作表。放弃原因：无法统一权限、审计与前端组件。

### 4. Condition 使用结构化字段而非任意脚本

- 条件模型：`field + operator + value`（如 amount > 100000），操作符白名单
  EQ/NEQ/GT/GTE/LT/LTE/IN/NOT_IN/CONTAINS，不存任意脚本。
- 安全性：避免注入任意表达式；可校验、可索引、可审计。
- `expression` 字段仅预留组合语义（如 A AND B），本轮不执行复杂布尔逻辑。
- 备选方案：直接存储 JS/JSON 表达式。放弃原因：无法静态校验、存在注入风险、难以做规则可视化与审批解释。

### 5. History 与 AuditLog 分开保存

- `WorkflowHistory`：业务视角的流转记录（stepNo、before/afterStatus、动作、耗时），
  供审批详情页展示"谁在什么时候做了什么"。
- `AuditLog`：安全视角的操作审计（actor、action、entityType、entityId、IP、meta），
  覆盖所有平台的增删改查，供安全审计与合规。
- 两者不合并：查询模式不同（History 按实例时间线；Audit 按操作者/实体全局检索），
  生命周期不同（History 随实例展示；Audit 长期保留）。
- 备选方案：合并为一张表。放弃原因：字段语义不同、写入频率不同（Audit 远高于 History），合并会拖慢审批详情查询。

### 6. Notification 使用统一事件模型

- `NotificationTemplate`（模板，code 唯一，支持变量占位）+ `NotificationMessage`（消息实例）
  + `NotificationChannel`（渠道配置）+ `NotificationLog`（发送日志）。
- 渠道枚举：SYSTEM / EMAIL / TELEGRAM / WEBHOOK（本轮仅建模与 CRUD）+ WECHAT / DINGTALK（预留）。
- 业务模块只写模板与消息，不关心渠道实现；后续接入真实发送（邮件/Telegram/Webhook/企微/钉钉）时只扩展渠道层。
- 备选方案：各模块直接调邮件/消息 SDK。放弃原因：渠道切换、失败重试、日志追踪无法统一。

### 7. Settings 三层 Key-Value + 加密标记

- SystemSetting / TenantSetting / UserSetting 三层，key 唯一（SYSTEM 全局唯一；TENANT 按 tenantId+key；USER 按 userId+key）。
- `dataType` 枚举 STRING/NUMBER/BOOLEAN/JSON/SECRET；`encrypted=true` 时 API 返回掩码（******），不返回明文。
- 税率等业务参数通过 Settings 配置，不写死（DEFAULT_TAX_RATE 环境变量兜底，默认 13）。

### 8. 本轮明确不实现（为 Sprint 4–7 留接口）

| 不实现项 | 原因 | 后续 |
| --- | --- | --- |
| 可视化流程设计器 | 基础 CRUD 可先行验收 | Sprint 3B+（拖拽编辑器） |
| 真实邮件/Telegram/Webhook 发送 | 渠道建模先行，避免外部依赖 | 接入渠道执行器 |
| 定时调度器 | 不需要 cron 依赖即可验收 | 定时任务执行器（超时/升级） |
| 超时自动升级 | 需要调度器支撑 | 与定时调度器一并交付 |
| 业务审批页面 | 无业务模块页面（3A 只做底座） | Sprint 4+ 随业务模块 |
| Sprint 3B 内容 | 菜单/文件中心/Dashboard 属另一批次 | Sprint 3B |

## 影响

- 新增迁移 `0004_workflow_foundation`（22 表 + 11 枚举 + 59 索引 + 13 外键）。
- 新增 21 个平台模块权限（workflow-definition / workflow-instance / approver / approver-group / notification-template / dictionary-type / system-setting 等），MANAGER 动作级授权。
- 新增统一 API 规范：`{ success, data, meta }` 响应、`{ success:false, error:{code,message} }` 错误、
  Zod 校验、后端权限、AuditLog、乐观锁 version、软删除、Prisma transaction、错误码常量、请求日志。
- Seed 新增 Workflow Definition（QUOTATION_APPROVAL / EXPENSE_APPROVAL 示例）与 Approver Group（DIRECTORS / FINANCE），幂等可重复执行。

## 对 Sprint 4–7 的影响

- 销售/采购/库存/财务模块直接引用 `WorkflowDefinition.code` 发起审批，禁止写死审批逻辑。
- 业务单据通过 `businessType + businessId` 关联实例；审批结果回写由业务模块监听实例终态。
- 新动作/新状态必须走统一枚举扩展；新业务表必须带统一审计字段（CTO 规则）。
- 税率、币种、单据规则等参数一律走 Settings，不写死。
