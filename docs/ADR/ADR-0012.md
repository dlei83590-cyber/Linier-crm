# ADR-0012：Item Master Foundation（ERP 核心主数据）

- 状态：Accepted（Sprint 3C-3 设计期，实现待 PR #8 合并后启动）
- 日期：2026-08-06
- 关联：ADR-0008（File Center）、ADR-0010（Supplier Foundation）、EVENTS.md、ARCHITECTURE_BASELINE v1.0
- 定位：**Item Master 是 ERP 核心主数据**，Sales / Purchase / Inventory / Warehouse / BOM / Production / Cost / Finance 全部引用它。

## 背景

Sprint 3C-3 原计划做常规 Item CRUD。CTO 审阅后（#2064）决定提升层级：不做简单 `Item`，而做 **Item Master**，
一次设计到位，避免未来销售/采购/库存/BOM/生产/成本/财务各模块各自建物料模型导致重构。
**宁可现在多设计一天，也不要以后重构。**

## 决策

### 1. Item 分类（ItemType 枚举，10 类）
FINISHED_GOOD（成品）/ RAW_MATERIAL（原材料）/ SEMI_FINISHED（半成品）/ PURCHASED_PART（外购件）/
ACCESSORY（辅料配件）/ SERVICE（服务）/ CONSUMABLE（消耗品）/ ASSET（资产）/ TOOLING（工装模具）/ PACKAGING（包装材料）。
以后扩展只加枚举值，**不加字段**。

### 2. Item 层级（五级）
`Category → SubCategory → Series → Model → Variant`（如 Linear Guide → SM → SMH45 → SMH45A → SMH45A-R1515）。
实现：`ItemCategory` 两级树（Category/SubCategory，自引用）+ Item 三级字段（series/model/variant）。
不把所有层级塞进 Item Name。

### 3. Item 标识体系（Identification）
InternalCode（唯一主编码）/ OEMCode / CustomerCode / SupplierCode / Barcode / QRCode / DrawingNo / Revision / Version。
图号（DrawingNo）与 File Center 图纸（attachmentType=Drawing）直接关联。

### 4. 多 UOM（非单一 Unit）
Stock UOM / Purchase UOM / Sales UOM 三个引用字段（复用 Sprint 2 `UnitOfMeasure`）+ `UomConversion` 换算表
（fromUom/toUom/factor，1 from = factor to）。采购公斤、库存件、销售套全部支持。

### 5. 规格独立（ItemSpecification）
`key / value / unit / sort` 的 KV 表，挂在 Item 下（onDelete: Cascade）。
不建几十个固定字段，导轨/轴承/油缸等任意品类均可表达。

### 6. 附件（复用 File Center）
不新建附件表。`FileAttachment.businessType=item`，attachmentType 枚举：Drawing / Manual / Certificate / Image / 3D Model。

### 7. 生命周期（ItemLifecycle）
DESIGN（设计）/ TRIAL（试产）/ MASS_PRODUCTION（量产）/ DISCONTINUED（停产）/ OBSOLETE（淘汰）。
停产/淘汰直接通过 lifecycle 控制（发布 ItemObsoleted 事件），业务模块据此拦截新单据。

### 8. Item Cost（只建接口，不做算法）
`ItemCost` 表 + costType 枚举：STANDARD（标准成本）/ LAST_PURCHASE（最近采购价）/ AVERAGE（移动平均）/ CURRENT（现行成本）。
金额 + 币种 + 生效日期 + 来源。**算法不在本 Sprint 实现**，Finance 后续引用。

### 9. 供应商物料（SupplierItem，不建 SupplierId 单值字段）
`SupplierItem`（itemId + supplierId + supplierCode / MOQ / LeadTime / Currency / PurchasePrice），
`@@unique([itemId, supplierId])`。一个 Item 多个供应商才合理；杜绝在 Item 上放单一 supplierId。

### 10. Domain Events（进 EVENTS.md，不后补）
ItemCreated / ItemUpdated / ItemObsoleted / ItemPriceChanged / ItemRevisionReleased。
Notification / BI / Webhook 监听，模块间不直接调用。

## 影响

- Schema（设计草案）：+7 模型（ItemCategory/Item/ItemSpecification/UomConversion/ItemCost/SupplierItem/ItemRevision）+ 4 枚举（ItemType/ItemLifecycle/UomUsage/ItemCostType）→ 预计 86 模型 / 41 枚举。
- 复用：UnitOfMeasure（Sprint 2）、BusinessPartner（Sprint 2）、File Center（Sprint 3B）、Tag（Sprint 3C-1，可选）。
- RBAC（实现期）：item 模块补全动作级权限 + 新增 item-specification / item-uom / item-cost / item-supplier / item-revision / item-attachment / item-category（8 模块）。
- API（实现期）：约 20 端点（items 主档 + specifications/uom-conversions/costs/supplier-items/revisions/attachments + item-categories 树）。
- 迁移（实现期）：`0011_item_foundation`（仅新增，不改既有表）。

## 权衡

- 五级层级（Category 树 + 三级字段）vs 单一扁平分类：前者支持任意品类细分，代价是查询多一次 join；本设计以查询性能换扩展性。
- ItemCost 单表 + costType 枚举 vs 每成本类型一表：单表支持任意成本类型扩展，历史留痕简单。
- 先设计后实现：CTO 明确要求 3C-3 今天只做设计（Schema 草案/ERD/ADR-0012/OpenAPI 草稿/EVENTS 更新），不写代码、不提交 PR。

## 待确认（CTO 决策项）

2. ItemCost 单表 + costType 枚举方案是否采纳？
3. attachmentType 枚举放 File Center 侧还是 Item 侧定义？
4. Item 是否复用 Tag 打标签（独立 ItemTag or 复用 PartnerTag 语义）？
5. 3C-3 是否同步补全 `item` 模块动作级权限（Sprint 2 仅 item:read/write）？
