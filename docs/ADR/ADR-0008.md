# ADR-0008: File Center（Sprint 3B）

- 状态：已接受
- 日期：2026-08-05
- 决策者：CIO + CTO 审核
- 分支：feature/sprint3-platform-capabilities

## 背景

报价 / 合同 / SO / Invoice / Project 等业务单据都需要附件与文件管理。
若各模块各自实现文件表，会导致：存储路径不统一、版本无法追溯、附件关联无法跨模块复用。

## 决策

### 1. 四个模型：Folder / File / Version / Attachment

| 模型 | 职责 | 关键字段 |
| --- | --- | --- |
| FileFolder | 文件夹（树形） | code/name/parentId（SetNull）/sort |
| File | 文件元数据 | code/name/originalName/extension/mimeType/size/storagePath/checksum/folderId/ownerId/currentVersion |
| FileVersion | 版本历史 | fileId+versionNo 唯一、originalName/mimeType/size/storagePath/checksum |
| FileAttachment | 业务附件关联 | fileId + businessType/businessId（报价/合同/SO/Invoice/Project 统一引用） |

- **File 只存元数据**；真实二进制存储（对象存储/本地磁盘）后续接入，`storagePath` 预留。
- Preview 能力：`GET /api/files/:id/preview` 返回可预览性（mimeType 白名单）+ 预览 URL，真实渲染后续接入。

### 2. 版本策略

- 创建 File 时自动生成 versionNo=1 的初始版本（事务）。
- 新增版本：`POST /api/files/:id/versions` 推进 `currentVersion`（事务，乐观计数）。
- 版本历史可追溯，软删除不物理删除。

### 3. 附件关联

- `FileAttachment`：`fileId + businessType + businessId`，同一文件对同一业务单据唯一。
- 查询：`GET /api/attachments?businessType=&businessId=`，业务模块直接复用。

### 4. 删除策略

- File → FileFolder：SetNull（文件夹删文件保留，提升为无目录）。
- FileVersion / FileAttachment → File：Cascade（文件删版本/附件删，逻辑上软删）。
- 业务上 DELETE 一律软删除（deletedAt），禁止物理删除（CTO 规则）。

### 5. 权限

- 新增 4 模块：file / file-folder / file-version / file-attachment，各 10 动作级权限；MANAGER 全量。

### 6. 迁移策略

- 新迁移 `0008_file_center`：4 表 + 索引 + 外键，仅新增不修改既有表（CTO 规则）。

## 备选方案及放弃原因

- **各业务模块独立文件表**：存储/版本/附件无法统一 → 放弃。
- **文件内容直接入库（bytea）**：数据库膨胀、备份困难 → 放弃，走对象存储（storagePath）。
- **单独 Preview 表**：预览是派生能力（由 mimeType 决定），不需要表 → 放弃，走 API 计算。

## 影响

- 新增 4 模型 + 迁移 0008；新增 4 模块权限。
- 报价/合同/SO/Invoice/Project（Sprint 4+）统一通过 FileAttachment 引用文件。

## 对后续 Sprint 的影响

- 业务单据只需创建 File + FileAttachment 即可获得版本/预览/附件能力。
- 对象存储接入（真实上传/下载）后续以渠道执行器方式扩展，不影响元数据模型。
